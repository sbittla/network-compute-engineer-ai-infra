# R2 — A mis-weighted competency: model answer

Any argument grounded in Table 24.7's recurring problems earns credit. Reference example:

**Claim.** For **AI Network Engineer at an AI-cloud / neocloud employer**, `automation` (weight 1) is
under-weighted. Table 24.7 lists that group's problems as *rapid GPU cluster deployment, bare-metal lifecycle,
tenant provisioning* and its interviews as probing *bring-up speed and acceptance testing*. A network engineer
there spends much of the job generating and validating configuration for hundreds of new leaves, which is
automation work. The real register agrees in direction: of the 8 AI-network roles on 2026-10-30, 3 were
front-end, deployment or network-automation roles asking for Python or Go automation
`[OBSERVED, 2026-10-30]` (Table 24.9).

**Proposed weight and effect.** Raise automation from 1 to 2. For the sample learner at senior (automation
d = 3, t = 2, fully met), Σw becomes 18 and Σ w·fraction 14.333, so readiness rises from 78.4 % to 79.6 %
`[MODELED]`. The status is unchanged (the observability gap of 2 still blocks "ready"), which is the honest
point: re-weighting changes emphasis, not the binding gap.

**Counter-case to acknowledge.** For a frontier lab, whose problems are collective performance and fault
tolerance of very large jobs, `congestion` and `rdma_fabrics` at weight 3 are probably right.

**Deductions.** Arguments from personal preference with no link to Table 24.7.
