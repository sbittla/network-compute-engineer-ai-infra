# Lab 8 — RDMA Deployment-Readiness Validator and perftest Analyzer

## 1. Goal and the real-world task it mirrors

Before a GPU node joins a training partition, someone has to prove that every one of its RDMA NICs is
configured the way the fabric expects — and that it actually performs. In production this is an
admission pipeline: collect command captures from the node, compare them with a baseline, run
perftest against a known-good peer on every rail, and block admission on any failure. In this lab you
build the two analysis halves of that pipeline:

1. **`readiness.py`** — parses per-node captures of `ibv_devinfo`, `rdma link`, `show_gids`,
   `ethtool -i`, `ethtool`, `ip -o link`, `ip -o -4 addr`, `dcb pfc`, `dcb app`, `lsmod`, and the site
   RDMA environment file for eight ORION nodes (`orion-n01`…`orion-n08`, `rack-01` and `rack-02`), checks them against
   `data/baseline.yaml`, and emits a READY / NOT_READY checklist report with evidence for every failure.
2. **`perftest_analysis.py`** — parses `ib_write_bw -a --report_gbits` and `ib_write_lat -a` results for
   32 node-pair/rail combinations, summarises bandwidth versus message size (plateau, n½) and latency
   percentiles, flags pairs that underperform the fleet, and correlates flags with a PCIe link-status
   capture.

The dataset contains planted faults of the kinds described in Chapter 8. Find them all with no false
positives. The perftest results come from the previous acceptance campaign (late September), while the
inventories were captured on 2026-10-12; treat them as independent evidence — configuration drift since
the campaign will not show up in the perftest data.

## 2. Tier and realism boundary

**Tier L1** (laptop; Python only; no GPU, NIC, or root). Every capture is synthetic, generated by
an instructor-side seeded generator (not shipped in the student release) to imitate real tool output closely; formats are abridged and vary by
version in real life. The perftest numbers are `[SIMULATED]` from a simple model
(BW(s) = 8s / (1/R + 8s/B), Manuscript Section 8.11). The lab proves you can parse, check, and reason
about RDMA readiness evidence. It does **not** prove that any NIC, cable, or switch performs as modelled
— only the L3 extension below produces measurements.

Rules of the checks (also in the docstrings): MTU fails if the netdev MTU ≠ 9000 **or** `active_mtu`
≠ 4096; GID_INDEX fails unless the index named by `NCCL_IB_GID_INDEX` resolves, on that device, to a
`v2` GID whose IPv4 equals the netdev's address; QOS_PFC fails unless PFC is enabled on exactly
`{3}`; ADDRESS_PLAN uses `10.100.{rail}.{2*node+1}/31`; PEERMEM is a node-level finding (device `-`).
Perftest flags: plateau = median `BW average` over sizes ≥ 1 MiB, flagged if < 0.90 × fleet median;
tail = median p99.9 over sizes ≤ 4 KiB, flagged if > 3 × fleet median.

## 8. Extensions: L3 hardware-backed variant

> **Safety:** Run only on nodes that are drained or in a dedicated lab/acceptance pool, with the
> fabric owner's agreement. Bandwidth tests saturate links and can trigger PFC pauses beyond the tested
> pair. Do not change switch configuration.

**Collect a real inventory** on each node (read-only; some commands need root or `CAP_NET_ADMIN`) into
`inventory/<host>.txt` using the same `### cmd:` section headers:

```bash
{
  echo "### host: $(hostname -s)"; echo "### collected: $(date -u +%FT%TZ)"
  echo "### cmd: ibv_devinfo"; ibv_devinfo
  echo "### cmd: rdma link show"; rdma link show
  echo "### cmd: show_gids"; show_gids            # vendor script; or read sysfs gids/ and gid_attrs/types/
  for ifc in ens1np0 ens2np0 ens3np0 ens4np0 ens5np0 ens6np0 ens7np0 ens8np0; do
    echo "### cmd: ethtool -i $ifc"; ethtool -i "$ifc"
    echo "### cmd: ethtool $ifc"; ethtool "$ifc"
  done
  echo "### cmd: ip -o link show"; ip -o link show
  echo "### cmd: ip -o -4 addr show"; ip -o -4 addr show
  for ifc in ens1np0 ens2np0 ens3np0 ens4np0 ens5np0 ens6np0 ens7np0 ens8np0; do
    echo "### cmd: dcb pfc show dev $ifc prio-pfc"; dcb pfc show dev "$ifc" prio-pfc
    echo "### cmd: dcb app show dev $ifc dscp-prio"; dcb app show dev "$ifc" dscp-prio
  done
  echo "### cmd: lsmod | grep -E 'peermem|mlx5|ib_core|ib_uverbs'"; lsmod | grep -E 'peermem|mlx5|ib_core|ib_uverbs'
  echo "### cmd: cat /etc/halcyon/rdma.env"; cat /etc/halcyon/rdma.env   # or your site's equivalent
} > "inventory/$(hostname -s).txt"
```

Adapt interface names, the baseline (`firmware`, `driver_version`, rails map, address plan), and the env
file path to your environment. On drivers where `dcb` does not reflect the NIC's QoS state, use the
vendor tool (for example `mlnx_qos -i <if>` on NVIDIA NICs) and extend the parser.

**Run perftest per rail** between two nodes (server first, then client):

```bash
# server (node B)
ib_write_bw -d mlx5_3 -x 3 -a -F --report_gbits
# client (node A), destination = node B's rail-3 address
ib_write_bw -d mlx5_3 -x 3 -a -F --report_gbits 10.100.3.5 | tee perftest/bw_n01-n02_rail3.txt
# latency
ib_write_lat -d mlx5_3 -x 3 -a -F                                   # server
ib_write_lat -d mlx5_3 -x 3 -a -F 10.100.3.5 | tee perftest/lat_n01-n02_rail3.txt
# PCIe status for the correlation step
lspci -vv -s <nic-bdf> | grep -E 'LnkCap:|LnkSta:'
```

Pin both ends to the NIC's NUMA node (`numactl --cpunodebind=<n> --membind=<n> ib_write_bw …`), run
at least **5 repetitions** per rail, discard a warm-up run, and report the median and min/max of the
plateau and of p99/p99.9 latency. Copy `manifest.yaml`, set `evidence_class: MEASURED`, and fill in every
field under `extensions[0].record` (firmware, driver, rdma-core and perftest versions, kernel, switch
model/OS, QoS summary, topology, NUMA binding, exact command lines, warm-up policy, run count, and any
other traffic on the fabric). Results without a filled manifest are not evidence.
